Running the two processes You have two separate processes: API SERVER server.ts │ ↓ PostgreSQL and: WORKER emailWorker.ts │ ↓ PostgreSQL │ ↓ Resend For example: # Terminal 1 npm run server and: # Terminal 2 npm run worker Your package.json could contain: { "scripts": { "server": "tsx src/server.ts", "worker": "tsx src/worker/emailWorker.ts" } } What happens during a normal purchase? Step 1 — Payment succeeds Your server generates: ABC123 Step 2 — PostgreSQL transaction BEGIN serials: ABC123 | john@example.com | John email_outbox: ABC123 | john@example.com | pending COMMIT Step 3 — Worker finds the job pending ↓ sending Step 4 — Worker calls Resend Worker ↓ Resend ↓ accepted Step 5 — Same worker updates PostgreSQL sending ↓ sent Final state: serials ──────────────────────────── ABC123 | john@example.com | John email_outbox ──────────────────────────────── ABC123 | john@example.com | sent What if Resend goes down? The worker does: sending ↓ Resend ❌ ↓ failed The row remains: ABC123 | john@example.com | failed The worker continues running. On its next pass: failed ↓ sending ↓ Resend If Resend is back: Resend ✅ ↓ sent What if the worker crashes? Suppose: pending ↓ sending ↓ 💥 worker crashes The PostgreSQL row still exists: ABC123 | sending When the worker starts again, the claimJob() query recognizes an old sending row: status = 'sending' AND last_attempt_at < NOW() - INTERVAL '5 minutes' and reclaims it. What if the worker crashes at the worst possible moment? This is the important case: Worker ↓ Resend ↓ ACCEPTED ↓ 💥 worker crashes ↓ UPDATE email_outbox never happens The database may still say: ABC123 | sending When the worker restarts, it retries the same request with the same idempotency key: license-email/ABC123 Resend's documentation says that when the same idempotency key is reused with the same payload, the request is treated as the same email operation and the same email ID is returned. Resend currently retains those keys for 24 hours. So this: Attempt #1 license-email/ABC123 ↓ Resend and: Attempt #2 license-email/ABC123 ↓ Resend are the same logical email operation during that retention window. What if PostgreSQL goes down? The worker tries: claimJob() ↓ PostgreSQL ❌ The worker catches the error: catch (error) { console.error( "Worker cannot reach PostgreSQL:", error ); await sleep(5000); } Then: wait 5 seconds ↓ try PostgreSQL ↓ still down ↓ wait ↓ try again When PostgreSQL comes back: PostgreSQL ✅ ↓ worker gets pending/failed job ↓ Resend The worker itself doesn't need to remember the job. PostgreSQL remembers it. The complete architecture CUSTOMER │ ↓ PAYMENT │ ↓ ┌───────────────┐ │ API SERVER │ │ │ │ createPurchase│ └───────┬───────┘ │ ↓ ┌─────────────────────┐ │ PostgreSQL │ │ │ │ serials │ │ ───────────── │ │ ABC123 │ │ john@example.com │ │ │ │ email_outbox │ │ ───────────── │ │ ABC123 | pending │ └──────────┬──────────┘ │ │ ┌──────▼──────┐ │ WORKER │ │ │ │ claim job │ │ ↓ │ │ call Resend │ └──────┬──────┘ │ ↓ RESEND │ ↓ CUSTOMER The important separation is: serials = permanent business data. email_outbox = durable email work. Worker = processor of that work. PostgreSQL = durable source of truth and job ownership. Resend = external email service. And you don't need a separate licenses table if your existing serials table already contains the serial, email, name, and activation information. One final caveat: Resend's idempotency protection is 24 hours, not forever. If you want to avoid blindly retrying an unresolved job after that window, your worker should eventually move an ambiguous old job to needs_review rather than automatically send it again.
